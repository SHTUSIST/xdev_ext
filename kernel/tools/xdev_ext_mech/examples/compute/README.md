# BPF compute examples

These programs are BPF versions of fixed CPU transforms of the mechanism layer. Each program is the `compute` member of the CPU class struct_ops type (`struct xdev_ext_cpu_mech_ops`), which the kernel calls once per batch when a CPU stage selects transform id `XDEV_EXT_CPU_XFORM_BPF` (10). The interface is specified in `Documentation/userspace-api/xdev_ext-compute.rst`; the fixed transforms the programs reproduce are in `io_uring/xdev_ext_mech_cpu_core.h`.

The examples only show that these transforms can be written in plain BPF and pass the verifier. Nothing here claims that a BPF transform is faster or slower than the fixed kernel transform; that can only be measured on physical hardware.

## The examples

| Source | Objects | Same output as fixed transform | Stage `arg1` (length change D) | Globals |
|---|---|---|---|---|
| `crc32c_check.bpf.c` | `crc32c_check_bytewise.bpf.o`, `crc32c_check_slice8.bpf.o` | `XDEV_EXT_CPU_XFORM_CRC32C_CHECK` (4); with `strip=1`, `XDEV_EXT_CPU_XFORM_CRC32C_STRIP` (2) | 0; `-4` with `strip=1` | `strip` |
| `crc32c_append.bpf.c` | `crc32c_append_bytewise.bpf.o`, `crc32c_append_slice8.bpf.o` | `XDEV_EXT_CPU_XFORM_CRC32C_APPEND` (1) | 4 | none |
| `xxh64_append.bpf.c` | `xxh64_append.bpf.o` | `XDEV_EXT_CPU_XFORM_XXH64_APPEND` (6) with stage parameter = `seed` | 8 | `seed` |
| `parse_check.bpf.c` | `parse_check.bpf.o` | the header check of `XDEV_EXT_CPU_XFORM_PARSE_STRIP` (5), without moving the payload | 0 | `hdr` (4..256, default 16) |

The CRC32C examples call no CRC kfunc (`bpf_xdev_ext_crc32c()` and `bpf_xdev_ext_frame_crc32c()` exist, but these examples do not use them). The bytewise objects look up one 1 KiB table once per byte. The slice-by-8 objects look up eight 1 KiB tables (8 KiB in all) once per eight bytes. Both read the tables from `.rodata` with every index masked to 0..255, so the verifier can prove each access in bounds. The CRC is `~crc32c(~0, payload)` stored little endian behind the payload, as in the fixed transforms. XXH64 is appended big endian, as in `XDEV_EXT_CPU_XFORM_XXH64_APPEND`.

`parse_check.bpf.c` checks that each frame starts with a header of `hdr` bytes whose first four bytes hold, little endian, the number of payload bytes behind the header. Moving the payload to the front stays a kernel operation: a session that needs the strip adds a second CPU stage with `XDEV_EXT_CPU_XFORM_PARSE_STRIP` and `arg1 = hdr` after the check (the KVM test runs exactly this two-stage session).

A check that fails returns `-EBADMSG`, as the fixed transforms do, and the batch completes with that error; a check never writes a byte. A stage with a non-zero length change cannot be followed by an NVMe or AF_XDP stage (CREATE returns `-EOPNOTSUPP`), the same rule as for the fixed transforms with a length change.

## How a program reads a frame of run-time length

The view kfunc `bpf_xdev_ext_frame_rw(ctx, pos, off, SIZE)` needs `SIZE` to be a verifier constant, while the frame length is known only at run time. Each example therefore reads a frame in pieces of constant size. Whole pieces (256 bytes for CRC32C, 32 bytes for XXH64) are read by an open-coded loop, `bpf_for()`, whose trip count is a run-time value. The remainder is read by a fixed sequence of smaller views: for CRC32C one view each of 128, 64, 32, 16, 8, 4, 2 and 1 bytes, taken when the matching bit of the remainder is set.

The algorithm of each example lives in a header (`crc32c.h`, `xxh64.h`, `parse.h`) that compiles both as BPF and as host C. `compute_example.h` maps the names `ex_frame_len()`, `ex_frame_rw()`, `ex_frame_set_len()` and `ex_for()` onto the kfuncs and `bpf_for()` in a BPF build. A host build supplies its own definitions of those names; the host tests compile the same headers with GCC against a mock of the kfuncs. `crc32c_table.h` is generated by `gen_crc32c_table.py` and checked in; do not edit it by hand.

## Build and run

```
make -C tools/xdev_ext_mech/examples/compute VMLINUX_DIR=<dir with vmlinux.h> CLANG=<clang> OUT=<dir>
```

`VMLINUX_DIR` holds the `vmlinux.h` of the target kernel, for example the `BUILD_DIR` of `tools/xdev_ext_mech`. Clang is used only to compile BPF bytecode. Attach an example and select it from a CPU stage:

```
xdev_ext_mech_ctl attach --obj OUT/xxh64_append.bpf.o --map xxh64_append_ops --pin /sys/fs/bpf/cpu --set seed=0x5eed
# stage: class XDEV_EXT_MECH_CLASS_CPU, direction TO_DEVICE, fd -1, arg0 10, arg1 8
```

Only one CPU struct_ops program is attached system wide, and every CPU session created while it is attached runs that program's `compute`. Each example also supplies `build` and `complete` that keep the class defaults, so the same attached object also serves CPU stages that select a fixed transform.

## Tests

- Host, no BPF compiler: `tools/testing/selftests/xdev_ext_mech/compute_examples/run.py`. It compiles the algorithm headers twice with `$CC` (bytewise and slice-by-8 CRC32C) and compares every output with the independent oracles of `tools/testing/selftests/xdev_ext_mech/xform_oracle.h` and with the fixed transform code (`xdev_ext_mech_cpu_apply()`): lengths 0..300 and the frame-size edges up to 4096, a frame capacity of exactly L + D, every corrupted byte of short sealed frames, and multi-frame batches. It also checks the table header against its generator and the record checks of the KVM validator.
- KVM, on a prebuilt strict-debug kernel: `tools/testing/selftests/xdev_ext_mech/compute_examples/examples_kvm.sh`. The guest loads every object with the verifier statistics log and records the verifier's processed-instruction count of each program. For each case it then runs the same inputs once through the fixed transform and once through the example, in sessions of CPU stages over user frames (lengths 1..300 and the frame-size edges in single-frame batches, and multi-frame batches of five layouts), with corrupted copies for the checks. The host validator compares the two runs byte for byte and with its own Python oracle.
